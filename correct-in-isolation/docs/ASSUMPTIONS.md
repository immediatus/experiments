# Assumptions of Part 1 (a shared signal)

Each row: what the model assumes, where the input comes from, and what changes if it is wrong.

| Assumption | Source or status | If it is wrong |
|---|---|---|
| Horizontal loop: desired = ceil(replicas x current / target); no action within 1 +- tolerance | Documented: Kubernetes HPA concept page; tolerance 0.1 by default, configurable | A different rule changes the rate, not the band's existence |
| Vertical loop: request = (1 + margin) x usage percentile; margin 0.15, percentile 0.9 | Documented: VPA flags page | The band moves with margin and q; T2 gives it for any q |
| In the rest band (T2, T20), the percentile written as q x mean usage per pod | Model choice for a pair at rest, whose usage history is flat; q is a parameter (1.0 to 1.5) | q is a property of per-pod usage variability; measure it |
| In the drift (T3, T4, T21 to T23), the recommendation is 1.15 x the 90th percentile of per-pod usage in a histogram of equally weighted samples, one per minute, decaying with half-life 24 h, buckets 5% wide, reporting a bucket's upper edge | Documented percentile, margin and half-life (flags page); equal weights and the bucket width as the current recommender implements them (read for understanding) | Different bucket widths move the factor per step by up to their width (the bracket of T4); different weights move the step interval |
| Recommendation applied to running pods at once in the drift traces (T3, T4) | Model choice. Documented: the updater acts when requests are outside the recommended bounds (from the 50th and 95th usage percentiles), or for pods older than 12 h when the recommendation differs by more than 10% (`pod-update-threshold` 0.1); new pods are admitted at the current target | Delays slow the drift; its direction is unchanged |
| The vertical update tolerance in the rest band (T2, T20): 0 for a steady load, 0.1 at most | Documented threshold; the bounds close on the target when the percentiles coincide | The band of T2 lies between the two columns; at q = 1 every target of 0.7 or less is outside both |
| Demand constant, or a daily sine of amplitude 0.1 to 0.6 (T23) | Trace inputs | A daily cycle speeds the drift (T23); the staircase interval is a steady-demand result |
| Request floor 0.025 cores, VPA's documented minimum CPU recommendation per pod; no replica ceiling | Documented default (VPA flags page, `pod-recommendation-min-cpu-millicores` 25); the ceiling is a trace input | A replica ceiling or a VPA minimum ends the drift earlier, at that bound |
| Memory-to-CPU coupling beta from published garbage-collection cost (Hertz and Berger, OOPSLA 2005) | Estimate: Java benchmarks of 2005, heap measured relative to the minimum heap, slowdown as total run time | T5 is an illustration of the order of magnitude, not a measurement of any service |
| Memory-to-CPU coupling beta from current collectors: cycle lower-bound overheads of five OpenJDK 17 collectors (Cai, Blackburn, Bond and Maas, ISPASS 2022), transcribed in model/gc_data.py | Estimate: geometric means over 16 DaCapo benchmarks, a lower bound on cycles, heap as a multiple of the minimum heap; elasticities from neighboring two-decimal values | T39 shows the order of magnitude and where the knee sits per collector; zero elasticities at large heaps are rounding, not proof of no coupling; ZGC's generational mode is unmeasured (OpenJDK 21's repetition covers the same five collectors) |
| The split pairing's structure (T118): collection CPU a function of the heap over the live set it traces; the live set follows load with share theta_L; observed memory follows the request with elasticity xi | Model choice; the benchmarks measure cost against heap over minimum heap, and report neither theta_L nor xi | With theta_L = xi = 0 the gain is 1/(1 - beta theta); with theta_L = theta and xi = 0 it is 1 + beta theta and never singular; a heap that grows into its limit makes it singular past xi = 1 - beta theta/(1 + beta theta_L) |
| The tail's scope (T113): the horizontal loop reads the mean of many pods, and nothing clips a sample | Model choice | At ten pods the reading varies by 19% at a shape of 0.55; a node's cores clip the spikes that carry the upper branches |
| A fix in transit (T119): the target or the scale-up tolerance changes in one step at a chosen hour, demand steady | Model choice | A gradual change or moving demand changes the path; the frozen count is the model's |
| Hidden memory (T103): the histogram also holds 200 samples at a multiple of the starting usage some hours before the start, weighted as the recommender weights them | Model choice; the decaying histogram is documented (half-life 24 h) | A recommender with a short half-life forgets sooner, and runs from the same visible state converge sooner |
| TLC specifications (tla/): integer demand and requests, rounding up, no histogram, every start from 1 to 30 replicas and seven requests | Model choice, Markov by construction | The specification omits the memory the simulation has, by design: it is the formal side's model |

# Assumptions of Part 2 (a shared time scale)

| Assumption | Source or status | If it is wrong |
|---|---|---|
| Pod loop: pods not yet ready, pending ones included, count at 0% on scale-up | Documented: HPA concept page | Without the rule the pod loop would order ahead of nodes, and the node loop would see more of the need at once |
| Saturated metric: a ready pod's utilisation is capped at its limit, so each round multiplies replicas by at most g = limit / target | Restated from "One Bit per Dead Time", Proposition 3 | With a metric that does not saturate, one round sizes the overload and nesting costs one node wait |
| Node loop acts only on unschedulable pods, every scan interval (10 s), and adds the nodes they need beyond nodes already being provisioned | Documented: Cluster Autoscaler FAQ ("How does scale-up work?"); its simulation is "quite simplified and may require multiple iterations", which the model ignores | More iterations add waits; the model is optimistic |
| Node provisioning 210 s; pod dead time 90 s | Trace inputs; FAQ: provisioning "usually ... 3 to 4 minutes" on GCE | T7 gives the result for 30 s to 600 s |
| No metric window, no stabilisation window on scale-up, no node startup taints or image pulls on new nodes | Model choice | Each adds to every round; the ratio nested / ample can only grow when a delay is added to the node path |
| Headroom as free slots at the start, not refilled during the overload | Model choice; documented overprovisioning refills by making pause pods pending, which itself waits a node time | Refill arrives a node time later, after the first rounds it was meant to cover |
| Separated case: the node loop provisions for the final need at the first pending pod | Counterfactual; no documented node loop can see the final need, since the pod loop does not know it under a saturated metric | It is the best the composition could do, not an available setting |
| The pod autoscaler's default scale-up policy: at most the larger of 100% of current replicas and 4 pods per 15 s | Documented: HPA concept page, "Default behavior" | Binds only when g exceeds 2 (T27 at a 30% target: 630 s against 600); results at g = 2 are byte-identical with and without it |
| Whole-node rounding: the node autoscaler adds whole nodes, leaving slots a later round can use | Model behavior following the FAQ's scale-up description | Proposition 8's bound is exact only with no slot left over at the start of a round; at hot targets rounding removes waits (T27 at 70%: 2,490 s against 2,700) |
| Scale-down, pod loop: a recommendation every sync (the current count inside tolerance); scale-down to the highest recommendation of the last 300 s, then no rate limit | Documented: HPA concept page, downscale stabilization window and default scale-down policy (100% per 15 s) | A longer window keeps pods as well as nodes; a second surge inside it is served at once (T28 below 300 s) |
| Scale-down, node loop: a node free of pods is unneeded; it goes after 600 s unneeded, empty nodes up to 10 per scan; none within 600 s of a scale-up; checks only when no scale-up is needed | Documented: Cluster Autoscaler FAQ (scale-down section and flag table) | The 50% utilisation threshold is not modeled because packed nodes are full or empty; with spread pods it decides which nodes go |
| Running pods packed onto as few nodes as possible, so free slots form whole empty nodes | Documented scoring: NodeResourcesFit MostAllocated scores toward packing (Resource Bin Packing page); the default profile is LeastAllocated (scheduler defaults), which spreads; the model is the bin-packing profile | Spreading leaves fewer empty nodes but exposes lightly used nodes to one-at-a-time drains that restart pods; the direction is not claimed |
| Two surges of the same size, the first an hour long, the gap measured from the end of the first | Trace inputs for T28 and T29 | A shorter first surge can bring the 600 s delay after a scale-up into play and push deletion later |
| Gaps exponential with mean 600, 1,800 or 7,200 s, independent of the setting (T30) | Trace inputs; memorylessness is an assumption about the workload, not a documented contract | Gaps with memory (daily cycles, bursts) can make a finite hold cheapest; Proposition 11 then does not apply |
| Cost linear: node-seconds held plus an exchange rate times seconds to capacity (T30-T32) | Model choice; the rate is the team's, swept from 4 to 256 node-seconds per second | A shortfall cost that grows faster than linearly weights the late rounds more and moves the break-even later |
| Spare nodes 58 in T30-T32, whatever the surge | Trace input taken from T28's first surge | Only the ratio N_s / (R tau_node) enters the break-even and the switch |
| Pod memory: stabilization window up to 3600 s; spare nodes hold only this workload's pods; cost in node-time only (T33-T35) | Documented: autoscaling/v2 API reference, stabilizationWindowSeconds "less than or equal to 3600 (one hour)"; the rest model choices | In a shared cluster empty nodes can serve other workloads and idle pods cannot; per-pod costs (licences, connections) tilt Proposition 13 back toward nodes |
| Weibull gaps, mean 1800 s, shapes 0.5 to 3, standing for clustered, memoryless and near-periodic surges (T36-T38) | Trace inputs; no production record of surge gaps is used | Proposition 15 holds for any gap with a density; only the windows and savings depend on the Weibull choice. A hazard that falls then rises can have several local minima |
| Node memory past the 3600 s window: Weibull gaps of shape 0.5 and 0.7, means 3600 and 7200 s, rates 200 to 1000; forever stands for 200000 s (T40) | Trace inputs; closed form only, no simulation, because the differences are comparable to the per-round latency the simulation adds | Proposition 16 holds for any gap with a density; only the savings depend on these inputs |
| Surge sizes (T94-T96): Pareto above k = 2, the surge that saturates the running pods at target 0.5, independent; the need taken as continuous on Proposition 9's ladder; scan and sync latencies left out of the closed forms | Model choice; the Borg 2019 trace shows Pareto exponents of 0.69 and 0.72 for job consumption, a different quantity | A tail that is Pareto only over a range, or bounded, has a finite mean shortfall; the closed forms then hold over the fitted range |
| Controller (T96): cost per surge = mean gap (3600 s) x slots held + price (100) x pod-seconds short; maximum-likelihood exponent from the fifth surge on; cover capped at 8 rounds; readings capped at k = 10, 20 or 50 | Model choice; the actuator is the CapacityBuffer replicas field | Drifting or headroom-dependent sizes break convergence; a cap that moves (node quotas) is not handled by the fixed-cap estimate |

# Assumptions of Part 3 (shared state)

| Assumption | Source or status | If it is wrong |
|---|---|---|
| A re-watch answered after the retained history has passed gets 410 Gone, and the client must LIST, then watch from the fresh version | Documented: API concepts page; history "in the last 5 minutes by default" for etcd 3 | A longer history raises the second-wave threshold by the change and the failed-state condition by twice the change (T10's conditions, in seconds of backlog) |
| A LIST occupies seats in proportion to the objects it returns; overload is queued | Documented: API Priority and Fairness page | Reject mode (429) with client backoff delays the re-watch the same way; the condition is on the delay, not on how it arises |
| One priority level, fair queuing among identical flows modeled as FIFO | Model choice | Isolating informers in their own level protects other traffic but not the informers' own storm |
| Queue wait limit: a queued request is removed and answered 429 after min(remaining deadline / 4, 1 minute), 15 s at the default 60 s request timeout (T41-T45) | Implementation, not on the flow-control page: apiserver server/filters/priority-and-fairness.go (getRequestWaitContext), RequestTimeout 60 s in server/config.go | T10-T12 are the idealized queue without it; with it the second wave starts at about the same cost and the sustained storm from 114 instead of 90 |
| Client backoff: one delay function per Reflector shared by watch retries, failed LISTs and the relist after 410; 0.8 s doubling to 30 s, jitter to [d, 2d), reset when more than 2 min since the last reset | Implementation: client-go tools/cache/reflector.go and apimachinery wait.Backoff / backoffManager | Other clients back off differently; the closed-form least run of rejections, ceil((R - W) / (W + 2 cap)), changes with W and the cap |
| Fair queuing sensitivity: each client its own flow, the system level's defaults (64 queues, hand 6, queue length 50), dispatch to the queue that has received least work | Bootstrap defaults: apis/flowcontrol/bootstrap/default.go (system-nodes flow schema -> system level); dispatch rule simplified from the KEP's virtual-time fair queuing | Within a few percent of one FIFO queue at every cost run (T41); flows with very different request mixes could differ |
| Relist after 410: a streaming list from the watch cache by default (WatchList, apiserver 1.34, client-go 1.35), the same seats as a list; on the fallback path a LIST at the last observed resourceVersion, unpaginated, from the watch cache, and a consistent read only if that also expires | client-go reflector.go (DefaultWatchErrorHandler, relistResourceVersion) | The LIST cost is a parameter; a cheaper LIST moves a cluster along T41's rows |
| Watch periods uniform on 300 to 600 s | The client library's reflector asks for a timeout of five minutes times a uniform factor from 1 to 2; a parameter, not a documented contract | The second-wave threshold uses the shortest period, the failed-state condition the mean |
| Watches stay current until they end (no event gap), cost of a re-watch 0.05 seat-s, LIST cost a parameter | Trace inputs | Fewer or narrower lists lower the LIST cost, and T10 shows where that moves a cluster; WatchList streaming holds the same seats as a list for its initial burst (APF documentation), so it lowers memory, not this cost |
| The retained history is the documented five minutes (T10 to T12, T41 to T46); T57 varies it to 150 and 75 s | Documented: API concepts ("Clusters using etcd 3 preserve changes in the last 5 minutes by default"; the contract promises only "a limited time"); informer watches are served by the watch cache, whose resize rule keeps 75 to 300 s at a steady event rate (apiserver source, read for understanding) | Every threshold falls with less history, and the wait-limited storm onset falls further than the closed forms (113 to 79 at 150 s) |
| The resumed version is as fresh as the watch's end | Implementation: a bookmark roughly every minute and 2 s before the watch deadline; the contract does not promise bookmarks | A version A seconds old leaves T_h - A for the delay; every condition holds with T_h - A in place of T_h |
| Paginated lists (T65): pages of 500 (the pager's default), each admitted after the full 15 s wait limit; the token valid for the history | Source: client-go reflector (paging off on the cache path) and pager (full-list fallback on Expired); documented: API concepts (410 on an unavailable continuation), kube-apiserver flags | Rejected and retried pages take longer; a cache snapshot or etcd may still serve an older continuation |
| Storm lifetimes (T66): the model of T41 run for 72 hours, ten seeds, sudden trigger | Model choice; a storm counts as sustained elsewhere when still running in hour 8 | Lifetimes near the onset are random; a longer horizon would show more storms at 114 ending |
| Isolation (T67): the informers' level gets a fixed share of capacity, no borrowing | Documented: APF lends unused concurrency between levels | Borrowing while others are idle raises the onset |
| Mixed sizes (T68): 1900 small and 100 large informers, large lists 20 or 100 times a small one, total forced work equal to the specimen's | Model choice, after kubelets listing their node's pods and controllers listing all | Other mixes and different watch periods are not computed |
| No bookmarks (T70): Poisson matching events per selector; watches of 300 to 600 s, at least the history; steady load without queueing; the specimen's backlog | Documented: bookmarks not promised (API concepts); KEP-956 motivation | Queueing makes re-watches older and the load higher; bursty events change the probability |
| The trigger forces a fraction of clients to LIST, arriving over a spread | Trace input; examples in the KEP: recovery of large clusters | Sharper triggers reach the failed state at lower LIST cost (T11) |
| List costs over a tail (T98): one cost per informer, Pareto with exponent 3, 2, 1.5 or 1.2 and a fixed mean; the storm boundary for the share rows taken at 2250 s, the simulated onset | Model choice; no measured distribution of collection sizes is used | Real collection sizes are bounded and grow with the cluster, which narrows the spread; one list that holds the server for minutes moves the boundary |
| Split controller (T99): 410s counted every 10 s over 60 s, split above 0.1 per second, merged after a hold with no 410; while split, LISTs and watches drain through their own shares of capacity with the same wait limit, no borrowing | Model choice; realizable with a FlowSchema matching the verb list, which a streaming list (verb watch) does not match | Borrowing between levels narrows the split; a classifier rule on initial events would be needed on the default path |
| Network partitions (tla/, Part 3): a partition cuts a watching informer off for up to a bound; the re-watch on healing is served at once | Model choice; field data puts partition repair at tens of minutes to hours (Alquraan et al. 2018) | A client that keeps its watch through a short partition never re-watches; one that reconnects to another server meets that server's history |
| Cascade (T105): one sudden wave forcing a third of the informers, each informer its own flow | Model choice, the share behind one zone or one server of three | A wave spread over time is weaker near the onset (Part 3, T47 waves) |
| Hold frontier (T104): the controller of T99 with the hold varied; three seeds for the band | Model choice | The band's edges are seed-dependent; its cause is not derived |

# Assumptions of Part 4 (a shared assumption)

| Assumption | Source or status | If it is wrong |
|---|---|---|
| A pod needs every matching webhook with failurePolicy Fail in order to be admitted | Documented: Dynamic Admission Control, "Failure policy" | With Ignore the edge disappears, and with it enforcement while the webhook is down |
| A webhook matching its own pods, or two webhooks checking each other's pods, cannot restart once all replicas are gone | Documented: good practices, "Avoid self-mutations" and "Avoid dependency loops" ("If both webhooks become unavailable at the same time, neither webhook can start") | None: the model encodes the documented case |
| The webhook needs cluster DNS to start (T13, third configuration) | Model choice, standing for any add-on the webhook needs; the documented example is networking or storage plugins | Replace DNS with the add-on the webhook actually needs |
| Failed nodes come back empty; a component is up while one replica is up | Model choice | Partial capacity, slow restarts and readiness gates change timing, not whether a cycle binds |
| Failure sets equally likely among sets of the same size; zones fail whole | Trace input for T13 and the closed form of T14 | Correlated failures make covering a cycle more likely than T14 gives |
| Two kinds of start-time edge: availability (a webhook with failurePolicy Fail must be up to admit the pod) and rejection (a running webhook's rules reject the pod) (T47) | Documented: Dynamic Admission Control, "Failure policy" ("An explicit rejection, correctly transmitted, always denies the API request, regardless of the failurePolicy setting"); good practices, "Avoid self-mutations" | A webhook that both needs itself and rejects itself has both edges; the rejection edge binds first |
| A rolling node upgrade drains the nodes one at a time through the Eviction API, each node back empty before the next; evicted replicas are replaced at once on a drained node if admitted (T47) | Documented: API-initiated eviction (429 when a PodDisruptionBudget would be broken; "Troubleshooting stuck evictions"); Safely drain a node | Parallel drains or replacements landing on nodes not yet drained lose replicas faster; pod start time is left out |
| Replacements placed by the scheduler (T58): the node being drained is cordoned, every other node is schedulable, spread picks the node with fewest pods and pack the most, ties to the lowest number | Documented: Safely Drain a Node ("marked it unschedulable"); Resource Bin Packing (MostAllocated); scheduler defaults (LeastAllocated) | Topology spread, affinity or resource fit can pull replacements elsewhere; requested resources are counted as pods |
| Backoffs (T60): a rejected creation fails the ReplicaSet's sync, requeued with the default controller rate limiter (5 ms doubling, capped at 1000 s); a container that crashes is restarted after 10, 20, 40 s, capped at 300 s; webhook first start 30 s, crash after 5 s, readiness 10 s, pod start 90 s | Source: ReplicaSet controller and client-go rate limiters (read for understanding); documented: Pod Lifecycle restart policy; timings are trace inputs | Any update to the ReplicaSet requeues it at once; another event during the outage shortens the wait |
| Binding over time (T61): node failures independent, exponential with mean 30 or 90 days; a lost replica is down for the 300 s toleration plus a 90 s restart, then returns on another node | Documented: Taints and Tolerations (tolerationSeconds=300); restart time a trace input; failure detection time left out | Correlated failures dominate; detection time lengthens the window and shortens the time to bind slightly |
| Heartbeats (T62): Lease renewed every 10 s, retries from 0.2 s doubling to 7 s, Unknown after 50 s, eviction after 300 s Unknown; each webhook call fails independently with probability q; 100 nodes in one zone; regime from the time-averaged unhealthy share | Documented: Leases, Node Status (50 s, and elsewhere 40 s), Nodes (eviction limits); q is a parameter | Correlated failures and the instantaneous share change the counts; node status updates every 5 min also count as heartbeats and are left out |
| Self-upgrade (T63): RollingUpdate with default maxUnavailable and maxSurge; the new version's pods rejected by the old rules | Documented: Deployments (rounding, defaults, progress deadline, no action on a stalled Deployment) | A configured maxUnavailable changes the loss; Recreate removes every old pod first |
| Fix sets (T64): every webhook Fail and excluding only its own namespace; a webhook matches another's pods with probability p, independently; one replica each on distinct nodes | Model choice; the default exclusion is documented by Kyverno and shipped by Gatekeeper | Real rules are not independent draws; the fewest fixes are exact for each graph, the cost of a fix is not modeled |
| The stuck-eviction remedy (T59): at each refused eviction the operator deletes the pod, which the budget does not govern | Documented: API-initiated Eviction, Troubleshooting stuck evictions | An operator who investigates first, as the same page suggests, finds the rejection edge and loses nothing |
| Random start-time graphs (T100, T101): 1,000 components, edge i -> j with probability min(1, c w_i w_j / (n E[w]^2)), weights equal or Pareto above 1 (exponents 2.5, 1.8); a full restart; T100's shares averaged over 30 draws, T101's from one; unseen and unrelaxable edges drawn independently at the given share | Model choice; real graphs are built, small and recorded only in part | The thresholds describe how danger scales as projects are added; a given cluster's graph must be read (T89) |
| Relaxation in order (T104): the greedy order of T101, prefixes relaxed | Model choice | A different order, or re-planning after each relaxation, changes the curve's shape before its end |
| Heartbeats behind a failing webhook (T62, T114): each call fails independently with probability q, at once or after the webhook's timeout | Model choice; the timeout is the webhook's timeoutSeconds, 10 s by default | Correlated failures change the spell lengths; a timeout leaves fewer renewals per grace period and moves full-rate evictions to lower q |

# Assumptions of Part 5 (a shared order)

| Assumption | Source or status | If it is wrong |
|---|---|---|
| Mutating webhooks run in no stable order; an IfNeeded webhook is called again if the object changed after its call; no call after that is guaranteed | Documented: admissionregistration/v1 field reinvocationPolicy ("will be called at least one additional time"), Dynamic Admission Control page ("may be called again"); the apiserver's reinvoker calls the chain a second time and returns | Under the weaker wording only commuting chains are safe (T15, 1 pass) |
| A webhook's match rules are tested against the object as it stands at its turn, in every round; a webhook not called in round 0 is never called later (T50 to T52) | Documented: the field promises a further call only "after the initial webhook call"; the mutating dispatcher's comment: "during reinvocation, a webhook will not be called for the first time"; object selectors read the current object | An implementation that called newly matching webhooks on a later round would repair a match link once, as a value link is repaired |
| The reinvocation pass keeps the first pass's order | Model choice; the contract allows reordering ("may be reordered to minimize the number of additional invocations"); the current implementation sorts configurations by name "to have a deterministic order" | Reordering the second pass can help or hurt one order; the worst case over orders is unchanged |
| Built-in mutating plugins, which the apiserver also re-runs, are left out | Model choice | They are further mutators in the chain; each adds to the depth when it enables or is enabled by a webhook |
| Webhooks modeled as pure functions of the object: a label webhook, a sidecar injector, a pull-policy setter (the AlwaysPullImages case), a digest pinner, a signer, a capability policy, a mesh init injector, an injector selected by a label | Model choice; patterns, not products | Webhooks with external state can differ between calls and are not idempotent; the documentation requires idempotence |
| Every order equally likely (T16's and T51's shares) | Estimate: the documentation promises no order; the current implementation fixes it by configuration name, so one cluster has one order per chain | The worst-case pass count does not depend on this; only the share does, and it then prices how names are chosen |
| A second admission sees the object as the first did: same namespace, identity and operation, every webhook reachable by a dry run (T52) | Documented: dry-run requests reach webhooks with sideEffects None or NoneOnDryRun | A webhook keyed on the requesting user or the operation can treat the copy differently |
| Two injectors (T71): chart defaults read from the charts (Istio Never; Vault, Linkerd and Gatekeeper set no reinvocation policy); configuration names from the templates, Vault's from its release name | Charts and manifests on their main branches | Charts can be configured otherwise; what Istio does to a container it sees is abstracted as one fact |
| Plugin order (T72): built-in mutating plugins, then MutatingAdmissionPolicy, then MutatingAdmissionWebhook, in every pass; policies taken in name order | Source: AllOrderedPlugins (read for understanding); the contract promises no order | A different implementation order changes which direction converges in one pass |
| Prevalence (T73): couplings uniform in [-c, c] with unit gains; start-time edges independent at probability p, no self-matching; fact graphs as T54 | Model choice | Real systems are not random draws; the shares describe the model's ensembles only |
| Cross-seam fixes (T74): the Part 2 specimen at targets 0.8 and 0.9; a load metric as a per-pod average of requests counted on arrival, which neither saturates nor waits for ready pods | Model choice; Part 2's reversal condition; HPA default scale-up policy | A metric counted from requests served saturates at capacity; a real load metric lags by its scrape interval |
| Priority levels (T75): default nominal shares from bootstrap/default.go, level capacity in proportion, no borrowing, the T41 specimen | Source: default.go; documented: APF shares | Borrowing raises a level's capacity while others are idle |
| Built-ins (T76): in-tree mutating plugins run before the webhooks in every pass; a later pass runs only after a webhook changed the object | Source: reinvocation.go, mutating dispatcher; documented: built-ins re-run after a webhook mutation | Only the built-ins the model writes as facts are computed |
| Digest pinning (T77): pod replacements at replicas over the node mean time between failures; tag moves Poisson; pin resolved at each pod's admission, pinned images left alone | Documented: Images (digests, admission controllers that mutate Pods and PodTemplates); Kyverno CanAutoGen (pkg/cel/autogen/support.go) and the legacy ClusterPolicy auto-gen | Scale-ups and rollouts add replacements; a tag that moves in bursts changes the distribution |
| Orchestrator (T102): each admission is the contract's two passes over a fixed order; the admitted object is fed back as a new dry-run admission; a common fixed point is an object every matching webhook leaves unchanged; a revisited object without one ends the iteration | Documented: dryRun admission with sideEffects None or NoneOnDryRun; the iteration is a model choice | Webhooks that remove what others add, or call outside services, can change between dry runs; pods a controller creates never pass through the orchestrator |

# Assumptions of Part 6 (the whole)

| Assumption | Source or status | If it is wrong |
|---|---|---|
| Symmetric coupling among n loops, steady-state gains, the relative gain as the signal test (T17, T53) | Model choice, the simplest matrix whose rank needs every loop | Real couplings are not symmetric; the construction shows the order is unbounded, not that a cluster has a high-order seam |
| Webhooks write facts once their prerequisite facts are present, idempotent, inflationary and monotone; reinvoked whenever the object changed after their call (T54 to T56) | Model choice; the general form of Part 5's value links | A webhook that removes facts is a conflict; a match link is Part 5's Proposition 30 |
| 150 random dependency graphs: 2 to 4 webhooks, 2 to 7 facts, each earlier fact a prerequisite with probability 0.35; seed 7 (T54) | Model choice | A different draw changes the counts per pass, not the agreement between count and simulation, which is a proof |
| The audit's specimens are those of Parts 1 to 5, one per seam (T18) | Model choice | Each verdict is a property of its specimen |
| Configuration names admission-signer, image-digest, sidecar-injector, and the renamings signer and zz-signer (T18, T55) | Model choice; the order follows the documented-in-source sort by configuration name | Any names give the verdict of their order; the count applies to it |
| Per-direction tolerance (T78, T81): the horizontal loop scales up above u_h (1 + tol_up) and down below u_h (1 - tol_down); steady load; 60-day runs, tolerance swept in steps of 0.01 | Documented: HPA tolerance section, HPAConfigurableTolerance GA 1.37 | A daily cycle changes the step and so the width needed |
